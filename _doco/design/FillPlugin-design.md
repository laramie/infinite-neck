# Fill Plugin

## Iteration 1 : initial design : features

We want to have a new plugin, following the patterns set in ArpeggioPlugin and TransposePlugin.

It will be called FillPlugin.

The work we want to make available to the command-line menu interface of FillPlugin intially duplicates the work that can be done in the HTML UI on the Fill menu page ("btnFillNotes", "divFillNotes").  That page drives two functions: 
    `NoteTableController::fillChord()`
    and 
    `NoteTableController:fillChord2()`

fillChord() scrapes the values from DOM widgets and calls fillChord2(), so we were hoping that FillPlugin will be able to call into fillChord2() or doFill().  However, if since the design features likely diverge quickly, we suspect too much would have to change within fillChord2() or doFill(), we are fine with there being parallel functions since they would call the same high-level primitives.   However, if features become useful or popular within FillPlugin, we may want to back port those to the HTML UI, in which case having them ride on the same secondary helper functions over the primatives would be an asset.  (We know the command-line presentation is written in the browser, but we prefer to think of it as a text/command like interface that modifies the model, and the the HTML UI presentation layer presents it in the DOM.)  Our current assumption is that it is safer to plan parallel code paths, and worry about refactoring later.


We also considered sharing code between FillPlugin and ArpeggioPlugin, but currently reject this notion, as the design guidelines around plugins favor having the plugins be separate, stand-alone modules that only depend on things like PluginManager.  The plugins should be like modules that can be authored by disparate teams without regard for the other plugin authors, just adherence to the Plugin standards.  We don't mind the plugins getting complicated or divergent, because they are intentionally not in the core code, and can be plugged in or not.

Let us discuss the features of FillMenu.

In addition to being able to fill the NoteTable model with NamedNotes, FillPlugin should also be able fill in SingleNotes, and eventually all the note types (except single MIDI highlight, which makes no sense).

Again, diverging code paths, but same philosophy: FillPlugin is affecting the model the way fillChord2() affects the model only.

FillNotes should also allow command-line menu options for: 
- restrict fill range to minFret and maxFret exactly as ArpeggioPlugin does.
- restrict fill range to minRow and maxRow (string rows), and eventually teach Arpeggio pluging these same two options, most like likely by copying code rather than refactoring.
- Selecting the target table as the Fill menu page does
- Selecting the note color class, since this can be done through the palette or the command-line menu today, both of which select an active radio button on the palette.  Currently the Fill menu page relies on noteChord and noteScale and noteRoot, and this is a good place to start for the earlier iterations.  We just want to keep in mind that any note color type may be used in the future, especially noteTransparent (Emboss, the note that plays most logically from the User perspective with the AutoColor action) and noteAutomatic (the magic color that uses the AutoColor scheme in effect but persists the color choice).
- the ability to attach "owner":"FillPlugin" to notes placed, so that FillPlugin can change these notes as the user goes through their design choices before they settle on the noteColors and stylenums they want.  Filled notes would be real model notes and wwould be persisted in the songfile.  However, there will be an additional Action on FillPlugin, "Commit Notes" that when executed, removes "owner":"FillPlugin" from all notes in the Song, so that those notes become indistinquishable from User-authored notes, and subsequent applications of FillPlugin don't erase those notes, but only add new ones.
- FillNotes should not overwrite a User note at that location and Note type in the model.  This is different than how the Fill menu page behaves today, and will likely stay a difference.  Yet another reason to have divergent code.
- FillNotes will also have deeper menus which allow the user to input chord names and mode names as strings that align to the chord and mode names available in Song.chartChord and Song.chartMode.  These are generated by Tonal.js, and should be the canonical string values, though Fill menu page uses slightly different versions, which we will align in a later sprint.  This input of note and chord names in FillPlugin is also out of scope for this sprint for that reason, and because we haven't defined the menu flow for digging through the hierarchical nature of the categories of chord names, which Tonal.js doesn't address, but which we will.  We just want to give a heads-up here that the menu may look, in its simplest form, like being able to say "C","Maj","7" which would correspond to the feature in the Fill menu page of having the Section be in rootKey of "C" and selecting dropDownChords option "Maj7...".  Again, ill-defined at this point, but wanted to state it in case it affects the design choices.
- FillNotes will have a "Clear" action which will clear all "owner":"FillPlugin" notes *for the current Section* only.
- FillNotes will have a "ClearSong" action which will clear all "owner":"FillPlugin" notes  for the whole song.
- For consistency, we will likely have "Clear" be run any time a User hits "Apply" for FillPlugin after having changed [minFret, maxFret, minRow, maxRow] for the current note type.  If the user chooses a different note type (SingleNote vs Highlight) then changed maxFret, subsequent Clears would only apply to the current note type (Highlight).  In this way, they can go through, note type by note type, and make edits.

## Iteration 2 : refinements

Your proposal to implement only one note type is correct.  However, we feel the correct single type to pick is SingleNote.
1) NamedNotes usefulness to the user is mostly fulfilled by Fill menu page.  
2) The shortcomings of that page have specifically to do with minFret, maxRow, etc, none of which apply easily to NamedNotes.  The true purpose of NamedNotes is that they show all possible notes with a note name, so the user can choose which one to play while seeing the whole set.  That is the fundamental reason for infinite-neck, as beginning musicians often learn chords and melodies only in "first position" which is the first frew frets, usually 0 to 4 inclusive, while most guitars have at least 12 frets, and advanced players use 24 frets fluidly.
3) We considered having a "Save Current Highlighted Notes As SingleNotes" as an option to ArpeggioPlugin, but in considering that design, came to the conclusion that having a dedicated FillPlugin that could do SingleNotes within the ranges of frets and strings (rows) was much cleaner and more reuseable, and didn't cloud the User's perception and coding realities of ArpeggioPlugin's notes being very transient.  So we wanted something with the feel of ArpeggioPlugin, but with the features of the Fill menu page, which transcending the limitiations of the Fill menu page really being suited to NamedNotes. 

For iteration 2, please write a new section "Iteration 2" in your document which reflects this choice, that SingleNote will be the target of the comming implementation, with other note types being a completely separate, later sprint.  

For our ease of readability, and consistency in iterations, your iteration 2 should repeat the points you made in Iteration 1, with this new information in mind.  

However, as part of the new information, you don't need to repeat your argument that the plugin should be completely separate implementation from fillChord, fillChord2 and so on.  Your take on that topic confirms our suspicians, and we wholeheartedly agree and accept the assumption that this will be a completely new implementation contained in FillPlugin, with only small changes to the current core as determined necessary by the coming iterations.

Also to be ignored in your Iteration 2 section is future sprint features around the deep chord/mode input.  That is documented in our Iteration 1 request and your Iteration 1 response and can be safely dropped.

Additional points:

- We thing the concept of "edit" for a note is very limited in our application.  When clicking on a note, a new color may be applied.  We think that is it.  So let us say that simply changing a note's color (and semantically, its "role"--chord, root, passing, chromatic, etc) does one of two things: either it strips "owner"ship from FillPlugin, or it changes color, but leaves the note at peril of being deleted by FillPlugin.  Both of these are acceptable at this point.  We fear that having the core code start twiddling with "owner" is brittle, and starts marrying NoteTableController and friends to Plugins, which we don't want.  So of the two choices, we'd prefer to have the user lose notes even though they thought they were coloring them.  This happens elsewhere and is caveat-emptor today: if a user clicks on a note in an Observer table, the note is simply lost on the next Section change.  We may get around to blocking that some day, but for now we leave it semantically open.  Listener tables have the same semantic issue: clicking on a note to delete it in a Listener doesn't delete it because it reemergees on Section update.  We are fine with these cases because they are beyond the intended uses (Observers are for Look-ahead/Look-behind, and Listeners are for translating mappings between tunings), and we don't want to block them as they may be redesigned as we implement recording for Listeners.

- On the other side of this, is a case where FillPlugin wants to create a SingleNote where one exists.  This would be a simple "no".  If a note exists at that cell, don't Fill it.

- We don't think it is possible to have two SingleNotes exist at one spot in just different colors.  This may be possible in the model, but would be tricky to pull off in the browser.  So a SingleNote should be considered to "own" a cell.  This isn't strictly true for Listeners and Observers, where we order the painting carefully to hide this possibility.  If there are code paths where FillPlugin will have a problem with this, please continue to press to have it clarified, showing the code path.

- Accepted: define `Commit Notes` as: remove `owner: "FillPlugin"` from all FillPlugin-authored notes in the whole song and leave every other field unchanged.  Include this rule and discussion in your Iteration 2 report.

- Accepted: your tight rules for point 3, Auto-Clear.  Include in your report.

- Accepted: if `noteAutomatic` is offered, resolve it at apply time to a concrete persisted color class.  This aligns with the current UI rule: the note color/role is immediately resolved and stored at the time of the note cell click.  Include in your  report.

- Accepted: Target table selection needs to be explicit.  This should be presented as an early option of type org.dynamide.select, so that the user see the selected table right in the menu.  Default should be same rule as ArpeggioPlugin: first table in myTunings that is not wired (Listener, Observer, ...).  Select options should be all tables that match this rule.

Please regenerate your recommendation for Iteration 2 as a stand-alone report, knowing that the information from Itertion 1 is still available, and taking into account the edits above.  We will then repond to Iteration 2 as the basis.


## Iteration 3 : details around Fill roles/colors

The role for the three note colors that will be placed follows the three Fill roles: [root, chord, scale] which are calculated based on the rootID, or rootKey.  

For the FillPlugin, the values hard-coded into the SELECT dropdowns should be migrated to Constants.js.  Leave the coding of dropDownChords and dropDownScales as is.  Simply extract their values to useful structs in Constants.js.  In a later sprint, we will get these to agree with the similar arrays output by Tonal.js which is a mature package with validated names we will be standardizing on, then at that later implementation reemitting the correct names and building dropDownScales and dropDownChords dynamically.  So the source of truth for chords and scales will be the arrays in Constants.js, and those will today duplicate and match the values currently in dropDownChords and dropDownScales.

Today, the Fill page uses noteRoot, noteChord, and noteScale to color the notes.  So we will need three options.  We envision a menu in FillPlugin: 

Let us say the user has gone in and selected noteAutomatic as the color that is represented on btnRestoreRbColor, that is, the color/role reported by PalettePresentation as the last color picked, or its default, noteTransparent

So we would see this on startup:

```
r) root [noteRoot]
    r) noteRoot
    l) last: noteTransparent
c) chord [noteChord]
    c) noteChord
    l) last: noteTransparent
s) scale
    s) noteScale
    l) last: noteTransparent
```
And we would see this if the user has selected noteAutomatic: 
```
r) root [noteRoot]
    r) noteRoot
    l) last: noteAutomatic
c) chord [noteChord]
    c) noteChord
    l) last: noteAutomatic
s) scale
    s) noteScale
    l) last: noteAutomatic
```        


To get this value, ask PalettePresentation for the last restorable button color role.  This should be available as "noteTransparent", "noteRoot", etc.  If not, PalettePresentation should be fixed to provide this cleanly while still doing its current job.  Double check that PalettePresentation is initialized properly, with the default value being noteTransparent.

In this way, the user can set it with the UI, or with /pr command-line, e.g. /prt or /pra 
or /prc1

The question this begs is: is there a way to drop into /pr menu to select these in the plugin, then pop out with the value, without introducing a very complicated or disruptive state push/pop mechanism to the menu and action handlers?  Like dynamicaly copying that menu subtree?  

It sounds messy.  If so, we'd go with the mechanism described above, since the command-menu is fast to navigate today.  User would do these sequences, which are clean, and fit with our long-term goal of being able to script these menus with stable commands.

Using the existing menu system, then the User would type (assuming we install FillPlugin at "f" fill, meaning command-line is "/fpf" ):

### Iteration 2 lingering questions

#### Cleanup Targets

- The targets for clearing will be as follows in this section. 

- The targets for any Filled notes would always be Current Section.  The only actions that apply across Sections are "Commit Notes" and "ClearSong".  So the targets would be: Current Section >> Selected Table >> row range + fret range >> roles

- When Clear is invoked, it applies to Current Section and Selected Table.

- When ClearSong is invoked, it applies across Sections for the selected table.

- When Commit Notes is invoked, it applies across Sections for the selected table.

- tables chosen should be tables with *no* wirings.  That way, if we add new wiring types, they won't be available.  If a table is Listened to or Observed, it would be still be available, since it is a main table that doesn't display anyone else's notes.

#### Role Targets

- The role targets are different than the role colors, e.g. noteRoot would be the color/role to provide for  root notes.  Whether to Fill, Keep or emit nothing (None) is a separate menu option.  That matches how the controls give the user options in the Fill page.  So we'd need options for Root, Chord, and Scale. 

- In a key of C major for example, the Root is C, but the C major "chord" is the set of notes C,E,G and the "scale" is C,D,E,F,G,A,B. So If you paint the scale, it hoses the chords, and if you paint chords and scales, they hose the root.  That is why the choices Keep and None exist: to preserve the options to have or not have the C as absent, painted in root color, in chord color, or in scale color.  This logic should be deducible from the existing Fill page.

- Ditch any discussion of dynamic messing around with command-line menus.  You've convinced us that it is non-trivial, so we'll go with the concrete menus. In other words: Approved: "Simple Command-Menu Approach".

- It looks like a full menu would be: 

```
r) root
    n) none
    k) keep
    r) role [noteRoot]
        n) noteRoot
        l) last
c) chord
    n) none
    k) keep
    r) role [noteChord]
        n) noteChord
        l) last
s) scale
    n) none
    k) keep
    r) role [noteScale]
        n) noteScale
        l) last
```

These are stable, because "last" is always last chosen through the UI or command-menu, and resolves when poping back out, as you said, so the value chosen can be show for role on the parent menu item.  The three values noteRoot, noteChord, and noteScale are stable because that is what they were specifically designed to mean since version 1.  Users can, in fact, change the color of noteChord etc. through the chosen system or user stylesheets on the Palette with "Customize".  But noteChord will always mean a note that implies it was chosen as being part of a chosen or filled chord.

We believe noteAutomatic stays as a resolved menu option value as "noteAutomatic", and is resolved to a concrete note* color at Fill time.  That is because noteAutomatic uses the note function to determine its color, so is unknown until filling a concrete cell.

We believe this implies: Approved: "option 1. Keep the child caption simple as just last, and let the parent property caption show the resolved current value."

#### Note types

- as agreed, we are only doing SingleNote. Other notes should be able to share cells, since that's how they were designed and are used.  Their sizes and z-order mean all can be seen simultaneously.  You only get one bend of the three (x3==nine) flavors, and a bend is a type of TinyNote so really you only get one of [Tiny,Bend:[bend-flavor*]]. And you only get one highlight of the two flavors. 

- So Filling a SingleNote fills in only where no User-authored SingleNote is present in a cell, and hoses any previously chosen FillPlugin-owned SingleNote in this Section/Table.  

- The "none" option hoses the FillPlugin-owned SingleNotes in this Section/Table and replaces it with nothing. 

- This rule is approved: "block placement only when a note at the same row + col exists with styleNum = Note.STYLENUM_SINGLE". 

#### Manual User recolor allowed but open to deletion

- NoteTableController knows nothing about "owner"

- Persistence layer may clean up "owner" Notes as long as predicate is owned by Plugin.  Keep as much knowledge in Plugin, and only put helper into Persistence layer if the logic of maintaining note arrays is necessary for safety.

- User clicking on a previously Filled note is not guaranteed to be persisted at all or even with that color.  Nor does it trigger the model adjusting "owner".

- User clicked Filled notes would still be findable for being cleaned up by FillPlugin, and should be.

#### Moving to Constants.js

Plan on moving values to Constants.js

Plan on a tiny builder for the select HTML elements on the Fill page, and wire it into the page the way other destination divs are handled, presumably at infinite-neck load time.  Do not follow the template or widget strategies we have begun using, but prefer a simple helper function that can be called the way other SELECTs are filled in.

#### PalettePresentation

- Approved: "PalettePresentation.getLastRestorableRbColor() returning { id, value, caption }"
