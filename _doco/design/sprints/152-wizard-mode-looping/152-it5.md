# sprint-152 Iteration 5

## Round 1 Request

We need a way in tutorial `strict` mode to let the User set the BPM.

Simply, we just want to add controls to the `.tutorialPromptWidgetRow`  before the `button data-action="tutorialLoopBeats"` and after the `button data-action="tutorialLastSection"`.

At startup, and in any normal state, the control is one button, with text "30bpm" if the Song.defaultBPM is 30.  It gets its values and is live just like `#transport > .bpm` and can even ride on the class update mechanism, which would give it the same text formatting for free, e.g. 
```
<span class="bpm">30<small>bpm</small></span>
```
It can be styled like `.tutorialNav` except with `white` background-color  not `#ffbf00`.

When that button is clicked, however, it is replaced by the controls from the File menu page:
```
<input type="text" name="txtBPM" id="txtBPM" size="4" value="80"><button type="button">✓</button>
```
though obviously a new name and id are needed, and the `value` attribute in this example just came from copying from DevTools.

On clicking the fake checkmark button, or any other loss of focus (which means it must be focused after the first button click), or other keyboard behavior already handled such as ENTER key, it sets the Song.defaultBPM (and whatever other state sets the actual BPM in the runtime).  If there are other side effects of setting the BPM from the File menu page controls, such as affecting the Looper, then the identical behaviors should be used here, hopefully by calling the shared handler. Then these controls get replaced by the original button again.
There is no "BPM:" label on the edit box and fake checkmark button for this instance.  The fact of them being where the "bpm" button was is sufficient.

This only applies in `strict` tutorial mode since in other modes this navigator/transport-substitute is not available.

Yes, please proceed to coding.  To be clear, the elements mentioned show up when we do the following sequence: 
- `/vpts`
- `ESC`
So it is the ESC escape key to close the command-line that causes the redisplay.  (When we close the command-line with `x` it doesn't happen.)  We'd want this case handled, too.


## Copilot Response

`/vpts` now hides the Instrument Caption, Song title, Section Caption and Widget Row, and they stay hidden after ESC. The Jest suite passes (1459 tests). I added no new test, because this change is only DOM calls and Jest here avoids jQuery. I didn't run it in the browser, so the `/vpts` then ESC check is yours.

**Cause:** your ESC observation pointed to the real cause. ESC runs `leaveFullscreen()`, which re-applies the Song's saved Layout flags. `/vpts` had hidden `#topControlsCaptions` and `.captionRow` directly without updating those flags. `#topControlsCaptions` holds the Song title, Section Caption and Widget Row, so ESC showed them all again. Closing with `x` never re-applies the Layout, so nothing came back.

**Change:** in `setTutorialMode()` in infinite-neck.js, switching to strict now calls `toggleCaptionRow(false)` and `toggleInstrumentCaptions(false)` on the Song's Layout. These hide the elements and save the flags into the current screen, so the hidden state also stays on ESC. If you save the Song afterward, it will open the same way. I didn't need separate calls for Song title, Section Caption and Widget Row, since the `CaptionRow` flag hides them all.

**Left alone:**
- Switching back to `none` or `wizard` does not restore the flags. Use SHIFT+A or the `/vs…` commands.
- Opening a Song that is already strict is unchanged and still follows its saved flags.
- Not tested: ESC calls `leaveFullscreen()`, which also re-shows `.dockable-handle`. I didn't change that. If the dockable handles reappear after ESC in strict mode, tell me and I'll hide them again there.

Made changes.

The design and sprint documents never decide whether floating windows are allowed in strict mode. The only strict-mode hints in them are indirect, and I found no text that settles it.

**What the documents say**

| Source | What it says | Bearing on floating windows |

| 138-it2-implementation-plan.md | Strict "default visible surfaces" are the top logo and menu bar, the prompt area, `fretTables`, optional chart surfaces and the bottom strip. | Floating windows and handles are not listed as visible. They also aren't listed as locked. |

| 138-it3-design.md and 138-it4-implementation-plan.md | ESC hides the command line but doesn't stop looping or exit the tutorial. | This is the only ESC rule. It says nothing about restoring other chrome, so the ESC re-show you saw was never specified. |
| 138-it1-copilot-design-review.md | Fullscreen hides `.container` and `.dockable-handle`. | That is the fullscreen model only, not strict. |
| 154-it1-analysis.md and 154-it4-implementation-report.md | Print docks floated windows on entry and doesn't re-float them on exit. | This is the one place floating is decided explicitly, and it covers print only. |
| sprints.md | Lists "Support for floating windows and panels" as a Version 2 feature. | It is a general feature, not tied to tutorial mode. |

**What this means for strict mode**
- A floated Instrument saved in a strict tutorial opens floated because Song-open applies the saved anchorage, and nothing in the tutorial code or documents prevents that.
- Strict-mode locking is described in terms of `.dockable-handle`, `resetTutorialChrome()` and the Layout flags. Floating is saved separately, in each table's `anchorage`.
- The handles reappearing on ESC comes from `leaveFullscreen()` calling `.dockable-handle` `.show()`. I didn't find that in any design document.

**One thing in my last change to check**
138-it4-implementation-plan.md says strict mode should "Keep left rail LooperLight and Instrument Caption visible". The existing `resetTutorialChrome()` already hides `.captionRow` and `.leftRailSectionStatusHost`. Another line, 138-it4-implementation-plan.md, says strict tutorials just see "the default one-row visible widgets". So the documents and the code disagreed before my change. My `toggleInstrumentCaptions(false)` follows what `resetTutorialChrome()` does and what you asked for, but it goes against that documented line. If "Instrument Caption" in that line means the `.captionRow`, you may want to revisit it. If it only means the LooperLight in the left rail, there is no conflict.

**Options for floating windows**
1. **Leave it undecided (what you described):** the author floats or docks windows before saving. This matches the documents and costs nothing.
2. **Document it as allowed:** add a sentence to the strict-mode help, since floating Instruments are a useful authoring tool. Handles would stay hidden unless the author chooses otherwise.
3. **Forbid it:** have strict mode dock everything on open, as print does, and keep handles hidden after ESC. This needs a design decision and a code change.

I'd pick option 2 and make the handles' ESC behavior consistent: a strict tutorial should either always show handles or never show them. If you want ESC to keep them hidden, that is a small change in `leaveFullscreen()` or the Layout.

## Decisions

We have updated the help file as recommended in option 2.  Other than that, it is left in the current state, which means a tutorial may be saved with floating windows, and they may be shown without handles, and ESC does show the handles, which means a strict User can show the handles and thus dock the windows, but never re-float them.

Another thing we see is that strict mode files don't show any left rail elements.  Also, wizard mode can show Section Status (S) but not instrument title (C).  This is also nebulous. It should be revisited.
