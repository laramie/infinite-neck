# Answers to numbered questions

1. Trigger conflict: `/fml` is currently list-all. Should list-all move to a new trigger (for example `/fms`) or be removed this sprint?

ANSWER: The conflict with `/fml` should be resolved as follows: 
- `/fml` retains `/ file > macro > list all`
- `/fmp` becomes `/ file > macro > printf` which accepts a string to print to the User log, or in the language of the implementation plan: 
  - Add `p) printf` with action `macroLog` and one input value.


2. `/fml` payload type: should it require a JSON string (example `/fml "message"`) or accept any JSON value and stringify objects?

ANSWER: In the fixed syntax, the question is: `/fmp` payload type.  Which should be that it is a string, in double quotes, and it should be expanded, or escaped: 

```
/fmp "simple message"
/fmp "expand this: ${key} ${sectionCount}"
/fmp "don't expand this: \${beats}"
```

3. Depth boundary wording: should depth 4 mean maximum active stack is 4 (recommended), or maximum of 4 nested calls beneath the root?

ANSWER: ACCEPT recommendation.

4. Unknown expansion names: should unresolved `${name}` stay literal, resolve to empty string, or fail the line?

ANSWER: Fail the line.

5. Verbose tracing for skipped lines: when verbose is on, should blank/comment lines be logged as skipped entries?

ANSWER:  No, silently skip the line, continue counting line numbers per original source as already specified in implementation plan.  Since `/fmp` is available, any needed debugging or logging statements can use that. 

6. Expansion scope for non-string arg values: if args contain numbers/booleans/objects, should expansion insert JSON stringification or JS-style string coercion?

ANSWER: Not sure, but result should be valid JSON, since requirement of calling command-lines in macros is that INPUT arg is valid JSON.

7. Validation strictness for `/fmc` object: should extra top-level keys beyond `macro` and `args` be allowed or rejected?

ANSWER: Reject with User log message.
