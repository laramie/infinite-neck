It would seem that floatRect is optional, since a table opened today lays itself out based on the space its html contents consume.  Since it will be saved on file save, that should be respected.  But if absent, the DOM should figure it out, given that we set top and left.  Also, we have shown that ToolDisplayOptions is optional, since it is only used when a Tool window has Frozen DisplayOptions. Taken together, it would seem that `tblExample_1` would be legal, and would be opened as docked.

## 9. Open design questions...":
  1. capture floatRect at-save-time-only.
  2. relative units is the way to go.  Be aware that we use `em` for everything we can, so that both the browser CTRL-+/- resizing, and our own resizing work together to give Users control over relative sizes of note fonts, UI menu fonts, and browser sizing.   So an `em` is not a great judge of screen width.  It would seem percentage would at least be viable across Users sharing songs.  Minor tweaks can be had by dragging tables around, and hopefully saving the song brings up the same positions on the same machine.  When a song is brought up on another User's machine, hopefully percentages get the main idea across, and that User and drag things to preference.  Along with the clamping functions to keep things from becoming undraggable offscreen, that should suffice.
  3. Our preference would be to leave every table in its order in noteTablesLayout and MyTunings.  Even clicking "visible" checkbox does not destroy this information, so the MyTunings is the real source of truth for everything available in the Song.  Our preference then points to a UX of docking a floated table (since all anchorage.floatRect info is saved) every time a move-up/move-down button is clicked, thus making that motion meaningful.  The table is docked, then moved apropriately.  If the User wants it floated, he clicks Float and floatRect, having been remembered, restored.
  4. The true singleton protection for Tool windows is that Tool windows are like system windows: we only have one Transport, one SectionDrawer, one View menu page, one Palette, and so on.  The idea was to use the plumbing and painting of Instrument NoteTables to provide singleton Tool windows that we would have hardcoded them in the system if they didn't smell exactly like small instruments.  However this way, any user can add a tuning, click on Tool, and have a single utility window that answers some reference need.  This cannot be said about instruments generally, though.  The idea with any non-Tool window is that as many instruments as can be modelled should be able to co-exist as instances, e.g. three guitars in the same tuning but different notes, two basses, four pianos, and so on, being a musical group or orchestra.  Additionally, we have Listeners and Observers.  But all of the above should be able to have an "anchorage" that is exclusively `floated|docked`.
