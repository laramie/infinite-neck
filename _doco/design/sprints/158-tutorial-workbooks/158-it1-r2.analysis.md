# Copilot Response

The Roles badges are not saved anywhere. They are recomputed from the Song's own data each time, so this is better news than my analysis said.

## What happens today

- `refreshFileMenuSongInstrumentBadges()` (infinite-neck.js) calls `renderSongInstrumentBadges(getSong())` (InstrumentRoleBadges.js). That function reads three things from the Song: `myTunings` (with each `fromBaseID`), `wirings` (to tell Main, Listener or Observer apart), and `noteTablesLayout` (for visible or hidden).
- The refresh runs on Song open and on the `TableVisibility:changed` and `TableLayout:changed` events (infinite-neck.js). That is why adding a tuning updates the badges at once.
- Save to Workbook stores the verbatim Song JSON from `getPersistentSongFile()`. That JSON already holds `myTunings`, `wirings` and `noteTablesLayout`. When you reopen the Song, the badges come back because the open path recomputes them.
- Nothing about badges is written into the Workbook entry. A Workbook row has no badges today, as sprint 157 decided.

## Saving to the Workbook and authoring a tutorial Workbook

- The Song text already contains everything needed to compute the badges. A tutorial author who builds or edits a Song in the app and saves it to the Workbook cannot get out of sync with the file.
- The Library build uses a separate Node function, `extractInstrumentSummaries` in update-song-list.js. It is a near twin of `getSongInstrumentSummaries`. The differences are that it reads the raw JSON, logs warnings, and skips tunings with no `fromBaseID`.
- **This corrects section 6 H6 of my analysis.** I said in-browser derivation would need that Node code lifted into a pure module. That is not needed. The badge code in InstrumentRoleBadges.js is already pure and falls back to raw `myTunings`, `wirings` and `noteTablesLayout`, so it also works on a parsed Song JSON that was never turned into a `Song` object.

## Showing badges in the Workbook listing

I recommend computing the summary at save time and caching it on the entry:

1. **Compute at save time.** In `saveSong`, parse the text and call `getSongInstrumentSummaries(parsedJson)`. Store the result on the entry as `entry.instruments`, as a derived cache of the Song, the same way I proposed for `entry.caption`. Also store `SectionCount` and `tutorial` level. Then `getView()` and `renderSongRow` can show badges and the progress badge without reading any Song text.
2. **Recompute on every path that adds a Song.** That means Save to Workbook and Open Workbook (`parseWorkbookFile`).
   - Do not trust `instruments` in a downloaded file. Recompute it from `song`.
   - This removes the "build-supplied only" restriction I gave in Q13, so the build tool adds nothing special for badges.
   - It also means a tutorial author who edits the course file by hand can't leave stale badges.
3. **Keep the cache out of the saved Song.** Like `comment`, it is Workbook-level data. The file would carry `instruments`, but the loader ignores it and rebuilds it.
4. **Test parity.** Add a Jest test that gives the same Song JSON to both `extractInstrumentSummaries` and `getSongInstrumentSummaries` and expects equal output. One difference remains: the build skips a tuning with no `fromBaseID`. The in-app call uses `allowUnknown: true`, so it shows `(unknown)`. Pick one behavior.

## Where this changes the earlier recommendations

- **H6 and Q13:** badges are derived in the browser from the Song, not supplied by the build.
- **Open point:** a downloaded Workbook that only shows badges after being opened in the app is fine. The Library build still produces its own badges for the Course row, as the union of roles across the Course's Songs.
- **No change** to the Song format, the build, or the sanitizer is needed for badges. The only touch is the Workbook save and parse paths (`saveSong`, `parseWorkbookFile`), plus the row renderer in WorkbookUI.js.
